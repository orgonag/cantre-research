# M3 Matching State Machine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add matching to `@cantre/core`. Given decoded M2 tiles and a stream of GPS
fixes and user actions, it decides which track the user is on and returns one `Result`
per state, with one of the nine statuses in spec §6. It never claims certainty the
evidence does not support: diamonds, nearby different railways and partly loaded data
all become explicit ambiguity, and a user lock is never silently switched.

**Architecture:** This is pure TypeScript inside `packages/core`, with zero runtime
dependencies, no DOM, no network and no storage. It adds two folders:
- `src/network/` decodes `cantre.tile/1` JSON objects into one in-memory `NetworkView`.
- `src/match/` holds the matcher, built from four pure layers:
  - candidate search;
  - per-candidate milepost (reusing M1's `interpolateMilepost` and `gpsMilepostBandMi`);
  - a selection policy;
  - a reducer, `reduce(state, event)`, plus `currentResult(state, nowMs)` for stale handling.

Every threshold lives in one exported, frozen `MATCH_CONFIG` labelled experimental.
Scenario replays (event lists with expected status sequences) are the acceptance tests.

**Tech Stack:** The existing M1 toolchain (TypeScript 6.0.3, Vitest 5.0.5, fast-check
4.10.2, ESLint 10.13.0, Prettier 3.9.10). No new dependencies.

**Spec:** [2026-10-23-cantre-v1-design.md](../specs/2026-10-23-cantre-v1-design.md):
- §6 (matching state machine and status table);
- §9 (scenarios);
- §13 M3 done-when: "Every status in §6 is reachable and asserted by scenario replays."

The acceptance cases are in [ACCEPTANCE.md](../../ACCEPTANCE.md), and the selection
contract is in [IMPLEMENTATION.md](../../IMPLEMENTATION.md#route-selection-and-user-control).
Cross-milestone names are in the [roadmap](2026-10-23-cantre-roadmap.md). The tile format
is in [`pipeline/schema/tile.schema.json`](../../../pipeline/schema/tile.schema.json) and
[pipeline/README.md](../../../pipeline/README.md).

## What the Saskatchewan network implies (M2 build, probed 2026-10-25)

This is planning evidence only; M5 measures it properly. Main-track chains were sampled
every 100 m over 89,677 points.
- **Another subdivision close by:** another subdivision's main track lies within 50 m for
  927 points (1.03 %), and within 25 m for 697 (0.78 %).
- **Another chain of the same subdivision close by:** another chain of the same
  subdivision lies within 25 m for 3,341 points (3.73 %). These are mostly branch nodes
  and chain ends.
- **Diamonds:** SK has 21.

So ambiguity is rare but real. It is concentrated where the owner said it matters:
diamonds and different railways running together.

## Global Constraints

- `@cantre/core` keeps zero runtime dependencies. No DOM, network, storage, timers or
  `Date.now()`. Time enters only through event timestamps and the `nowMs` argument.
- Units follow the roadmap:
  - metres for every `…M` name and for `s`;
  - miles for `mp`;
  - `METRES_PER_MILE = 1609.344`;
  - milliseconds for every `…Ms` name;
  - degrees for `…Deg`, with bearings measured clockwise from north in [0, 360).
- The `MilepostResult` from M1 is reused unchanged. `Anchor` gains
  `tier: AnchorTier` with `AnchorTier = 'posted' | 'tc' | 'unverified'`, as the roadmap
  contract says.
- Every numeric threshold is in `MATCH_CONFIG`, which is frozen, exported and documented
  as experimental. The defaults:
  - `searchRadiusMinM: 50`, `searchRadiusAccuracyFactor: 3`, from spec §6: radius =
    max(50 m, 3 × accuracy);
  - `indistinguishableMinM: 10`, from spec §6: within d_min + max(accuracy, 10 m);
  - `staleAfterMs: 15000`;
  - `headingMinSpeedMps: 3`;
  - `headingToleranceDeg: 30` (Decision 2);
  - `continuityMaxMs: 5000` (Decision 3).
- Reason codes are `SCREAMING_SNAKE_CASE` string literals from one closed exported union,
  `MatchReason`, each documented. No free-text reasons.
- Honest outputs, from spec §2:
  - A null milepost is never zero.
  - Nothing is extrapolated or interpolated across a gap between intervals.
  - A user choice changes the candidate set but never the reported accuracy.
  - No probability or confidence score is invented.
- Determinism: the same network and the same event list give deep-equal results.
  Candidates sort by `(residualM, chainId ?? '', segmentKey)`.
- Fixes with non-finite values, latitude/longitude outside `CANADA_ENVELOPE`, negative
  accuracy, or a timestamp that does not increase are ignored. They never change the
  state, and they are counted in `state.ignoredFixes`.
- Every exported function has a doc comment giving its rule, units, source (spec section)
  and limits. Every non-obvious line of maths has a comment.
- Coverage thresholds stay at the M1 levels (95 / 90 / 100). LF line endings.
- Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Decisions beyond the spec

1. **Tile decoding lives in core.** `networkFromTiles` decodes `cantre.tile/1` objects as a
   pure function, with no fetching. M4's `@cantre/data-client` fetches, caches and
   version-pins tiles, then calls it. The roadmap line "mirrored as TypeScript types in
   `@cantre/data-client`" becomes "defined in `@cantre/core` (`src/network/`) and reused
   by `@cantre/data-client`".
2. **The heading filter.** It applies only when `speedMps > headingMinSpeedMps` and
   `headingDeg` is present. It drops a candidate whose track bearing at the projection
   differs from the heading by more than `headingToleranceDeg`, measured axially. Axial
   means modulo 180°, because a train can run either way; this is spec §6's
   "direction-agnostic". If the filter would drop every candidate, it is not applied, and
   the result gets the reason `HEADING_INCONSISTENT`.
3. **Continuity.**
   - **Ambiguity:** the previously matched chain resolves an ambiguity between candidate
     groups only when it is itself in the indistinguishable set I and no diamond rule
     applies. The reason is `CONTINUITY`.
   - **Contradiction:** when the previous chain is still within the search radius but
     not in I, the match holds for up to `continuityMaxMs` from the first contradicting
     fix. The milepost is shown, with the reason `CONTINUITY_HOLD`. After that limit the
     result is re-selected with no continuity.
   - **Lifetime:** continuity never applies across a `STALE` gap or any non-`MATCHED`
     result, and never outside the radius.
4. **Candidates.** There is one candidate per chain: the best projection onto the
   chain's full geometry (M1 `projectOntoPolyline`). There is also one candidate per
   **unchained** segment (sidings, yards, spurs) within the radius. A chain candidate
   carries `s`; a segment candidate has `s: null` and never a milepost. Groups for
   ambiguity are keyed by `(subdivisionNid, operator)`, and an operator is a chain's
   operator set joined in sorted order.
5. **Partial coverage.** The search disk counts as covered when the disk's bounding box,
   inflated by the radius in metres, lies inside the union of loaded tile bounds. Tile
   bounds are unbuffered. If the disk is not covered and exactly one group is in I, the
   result is `AMBIGUOUS_ROUTE` with the reason `PARTIAL_COVERAGE` (spec §6: a sole
   candidate in a partly loaded tile blocks automatic selection). If the fix lies outside
   every loaded tile, the result is `NO_COVERAGE`.
6. **The diamond rule.** A diamond position on any candidate chain within the search
   radius is measured as an along-track distance on that chain. If one is within
   `radius` of the candidate's `s`, the diamond blocks automatic selection. The result
   is then `AMBIGUOUS_ROUTE` with the reason `DIAMOND_NEARBY`, even when one line is
   closer, unless a lock resolves it.
7. **Locks.** A lock is `{ kind: 'chain', chainId }` or
   `{ kind: 'subdivision', subdivisionNid }`. Only candidates inside the lock are
   eligible.
   - **Lock matched:** the lock's best candidate is in I, computed over all candidates.
     The result is matched, with `selectionOrigin: 'user'`, even at a diamond.
   - **Lock conflict:** the lock has no candidate within the radius, or its best
     candidate is outside I. The result is `LOCK_CONFLICT`, with the lock kept and
     `milepost: null`.
   - **Clearing:** only an `unlock` event clears a lock. A new `lock` event replaces it.
8. **Milepost for a chain candidate.**
   - **Inside an interval:** if `s` lies inside an interval of that chain (by its first
     and last anchor `s`), the result is `interpolateMilepost(s, interval)`. Its band is
     `gpsMilepostBandMi(accuracyM, lower, upper)`, and its tier is the lower-ranked of
     the two bracketing anchors.
   - **Before the first or after the last interval:** `interpolateMilepost` on the
     nearest interval returns `BEFORE_FIRST_ANCHOR` / `AFTER_LAST_ANCHOR` (uncalibrated).
   - **Between two intervals:** `milepost: null`, with the reason `DISCONTINUITY_GAP`.
   - **No intervals on the chain:** `milepost: null`, with the reason
     `CHAIN_UNCALIBRATED`.
9. **The `MATCHED_SUBDIVISION` range.** When I holds one group with two or more
   candidates, take each chain candidate's calibrated MP. If all of them are calibrated
   and `max − min ≤ max(band)`, the result is `mpRange: { lowerMp, upperMp }`, with no
   single milepost. Otherwise `mpRange: null`, with the reason `TRACK_MP_DISAGREE` or
   `TRACK_UNCALIBRATED`. Segment candidates in the group, being unchained, make the range
   null with the reason `TRACK_UNCALIBRATED`.
10. **Time.** `currentResult(state, nowMs)` returns `STALE`, carrying the last full result
    as `historical`, when `nowMs − lastFixTimestampMs > staleAfterMs`. `fixAgeMs` is
    `nowMs − lastFixTimestampMs`.

## Review Focus

1. **Approaching, stopping at and leaving a diamond.** No automatic match may be shown
   while the diamond is within the radius, including during standstill with a stale
   heading. Leaving it must re-select from evidence, not from the approach line alone.
   Covered by the scenario in Task 7.
2. **A lock near a different railway.** With a lock set, a fix that is closer to the
   other railway gives `LOCK_CONFLICT`. It must never silently match the other railway,
   and it must never drop the lock. Covered in Tasks 6 and 7.
3. **A fix arriving out of order or late after a stale gap.** An older timestamp is
   ignored. After `STALE`, the next fresh fix re-selects with no continuity carried over.
   Covered in Task 6.
4. **Crossing a tile edge.** A chain decoded from two tiles must be one candidate with
   continuous `s` and no duplicate vertices. Mixed `datasetVersion` across tiles must
   throw. Covered in Tasks 2 and 7.
5. **A huge accuracy radius** (for example 300 m, which gives a 900 m search radius) must
   produce ambiguity or a plain match from the rules. It must never shrink the radius and
   never give a match narrower than the evidence. Covered in Task 5.

**Interfaces:**
- `TileBounds = { south; west; north; east }`, in degrees.
- `NetworkChain` is `{ id, subdivisionNid, subdivisionName, operators: readonly
  string[], cycle, pts: readonly LatLon[], sM: Float64Array, cumulativeM: Float64Array
  }`. It is the whole chain as far as it is loaded.
  - `sM` holds the stored `sMm / 1000` values.
  - `cumulativeM` is `sM` rebased so that `cumulativeM[0] = 0`, for M1's
    `projectOntoPolyline(p, pts, cumulativeM)`. The candidate's `s` is
    `sM[0] + alongM`.
  - If the loaded pieces of one chain are not contiguous (a gap in vertex indices
    because a tile is missing), the decoder keeps them as separate `NetworkChain`
    entries with ids `chainId`, `chainId#2`, … in vertex order, and `chainBaseId` holds
    the original id.
- `NetworkSegment` is `{ key, chainId: string | null, trackClass, status, subdivisionNid,
  subdivisionName, operator, geoAccuracyM: number | null, pts: readonly LatLon[] }`.
- `NetworkInterval` is `{ id, chainId, anchors: readonly Anchor[] }`, with anchors in
  `s` order and `tier` carried through.
- `DiamondPosition` is `{ assetId, chainId, sM }`.
- `NetworkView` is `{ datasetVersion, coverage: readonly TileBounds[], chains,
  segments (unchained only), intervals, diamonds }`. Everything is sorted by id for
  determinism.
- `networkFromTiles(tiles: readonly unknown[]): NetworkView`.
  - It validates the fields it reads, and throws `INVALID_TILE` with the path on bad
    input.
  - It throws `MIXED_DATASET_VERSION` when tiles disagree.
  - It delta-decodes `latE6`, `lonE6` and chain `sMm`.
  - It merges pieces of one chain by `vertexStart`. Overlapping vertices must be
    identical in `latE6`, `lonE6` and `sMm`, else it throws `TILE_MISMATCH`.
  - It de-duplicates intervals, anchors, segments and assets by id across tiles. Any
    duplicate must be deep-equal, else `TILE_MISMATCH`.

### Task 5: Selection policy

**Files:**
- Create: `packages/core/src/match/select.ts`.
- Test: `packages/core/test/match-select.test.ts`.

**Interfaces:**
- `SelectionInput` is `{ net, fix, candidates, coverage, diamonds, lock: Lock | null,
  previous: { chainId: string; sinceContradictionMs: number | null } | null, cfg }`.
- `Selection` is `{ status: Exclude<MatchStatus, 'NO_PERMISSION' | 'NO_FIX' | 'STALE'>,
  chosen: Candidate | null, group: readonly Candidate[], selectionOrigin: 'auto' |
  'user' | null, reasons: readonly MatchReason[], contradictionStartMs: number | null }`.
- `selectCandidate(input): Selection`, applying these steps in order. The first step
  that settles the status wins.

```text
1. coverage 'outside'                       → NO_COVERAGE (OUTSIDE_LOADED_TILES)
2. no candidates                            → OFF_NETWORK (NO_CANDIDATE_IN_RADIUS)
3. heading filter (Decision 2) → C'         (HEADING_USED / HEADING_INCONSISTENT)
4. d_min = min residual in C'; I = {c ∈ C' : residual ≤ d_min + max(accuracy, indistinguishableMinM)}
5. lock set (Decision 7):
     L = lock's candidates in C'; none → LOCK_CONFLICT (LOCK_NOT_SUPPORTED)
     best(L) ∉ I → LOCK_CONFLICT (LOCK_NOT_SUPPORTED)
     else I := I ∩ L; origin 'user'; LOCKED_BY_USER; skip 6–8
6. diamonds near any candidate in I         → AMBIGUOUS_ROUTE (DIAMOND_NEARBY)
6b. previous chain in C' but ∉ I, and now − contradictionStart < continuityMaxMs
                                            → MATCHED on the previous chain (CONTINUITY_HOLD)
7. groups(I) by (subdivisionNid, operator):
     > 1 group: previous chain ∈ I → keep its group (CONTINUITY)
                else → AMBIGUOUS_ROUTE (MULTIPLE_ROUTES)
8. coverage 'partial' and one group         → AMBIGUOUS_ROUTE (PARTIAL_COVERAGE)
9. one group, one candidate                 → MATCHED
   one group, several candidates            → MATCHED_SUBDIVISION (MULTIPLE_TRACKS)
```

  `chosen` is the single candidate for `MATCHED`, and null otherwise. `group` is the
  surviving candidate set I, used by the result to build the range or the choices.

**Interfaces:**
- `MatchEvent` is one of:
  - `{ type: 'fix', fix: Fix }`;
  - `{ type: 'permission', state: 'granted' | 'denied' }`;
  - `{ type: 'locationError', code: 'UNAVAILABLE' | 'TIMEOUT' }`;
  - `{ type: 'lock', lock: Lock }`;
  - `{ type: 'unlock' }`.
- `Lock` is `{ kind: 'chain'; chainId: string } | { kind: 'subdivision'; subdivisionNid:
  string }`.
- `MatchState` is read-only and immutable, with `ignoredFixes: number`.
  `initialMatchState(net, cfg = MATCH_CONFIG): MatchState`.
- `reduce(state, event): { state: MatchState; ignored: MatchReason | null }` is pure, and
  never mutates its input.
- `Result` is `{ status: MatchStatus, candidates, chosen, s, milepost: MilepostResult |
  null, mpRange: { lowerMp: number; upperMp: number } | null, mpBandMi, tier, anchorIds,
  selectionOrigin, lock, reasons, accuracyM, fixAgeMs, datasetVersion, historical: Result
  | null }`. `MatchStatus` is the nine spec statuses.
- `currentResult(state, nowMs): Result` (Decision 10).

**Rules:**
- **Before any fix:** the state starts as `NO_FIX` (`NO_FIX_YET`). Denied permission
  gives `NO_PERMISSION` (`PERMISSION_DENIED`) until it is granted. A `locationError`
  before any fix gives `NO_FIX` (`LOCATION_UNAVAILABLE`).
- **Each accepted fix:** the reducer runs `findCandidates`, `coverageOf` and
  `diamondsNear`, then `selectCandidate`, then `milepostFor` for the chosen candidate
  (or for each candidate in the group when the status is `MATCHED_SUBDIVISION`). It
  stores the full `Result`.
- **Continuity across fixes:** `previous` is set only from a `MATCHED` result. It is
  cleared by any other status, including a diamond `AMBIGUOUS_ROUTE`, and by `STALE`, so
  leaving a diamond re-selects from evidence alone. `continuityMaxMs` is measured from the timestamp of the first
  contradicting fix.
- **Locks:** a `lock` or `unlock` event re-evaluates the last accepted fix immediately,
  if one exists.
- **What a `Result` never does:**
  - it never carries a `milepost` unless the status is `MATCHED`;
  - it never carries an `mpRange` unless the status is `MATCHED_SUBDIVISION`;
  - `accuracyM` is always the fix's own value.
